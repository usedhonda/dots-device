# Dotへ渡す指示テンプレート

端末のファームウェアだけでは、通常の会話から要約や質問が自動で届くようにはなりません。自分のDotに端末プラグインを接続し、以下を保存する指示として渡してください。保存先や使える機能はDotの環境に依存します。接続権限と回答イベントの購読は、指示とは別に設定します。

これは実際の開発で必要になったルールを一般化したテンプレートです。個人の会話記録や特定の端末IDは含みません。

## 通常会話と端末への表示

以下を自分のDotへ渡します。

```text
通常の会話は、このチャットを主なやり取りとして続けてください。
通常のチャット返信を先に送ってください。

返信に新しい内容や進捗がある場合、返信の直後に、その要点を
24 Unicode文字以内の短い日本語にして device_publish_summary で
端末へ1回送ってください。文字数には句読点や空白も含めます。
既に受領済みの回答表示を残すために、新しい要約を省略しないでください。
挨拶だけ、同じ内容の繰り返し、新情報がない返信では送信を省略して構いません。

各返信後に、内部で次のどれかを必ず判断してください。
・要約を送信した
・新情報がないため省略した
・未回答の質問を保護するため省略した
・通信失敗のため省略した
送信を始めていない状態を、成功や通信失敗として記録しないでください。

未回答の質問を端末に出している間は、その質問を要約で覆い隠さないでください。
自分が出した質問と、その回答・受領状態を区別して管理してください。
回答を受領したあとは、後の新しい会話の要約で受領表示を更新して構いません。

端末が不在、オフライン、タイムアウト、または端末との通信が失敗した場合、
その端末処理を静かにスキップし、通常の会話を続けてください。
端末の接続エラーや再接続の依頼を通常チャットに出さないでください。
送信前に端末の状態確認だけを何度も行わず、送信のループ再試行もしないでください。
失敗した古い要約をためたり、後からまとめて送ったりしないでください。
送信結果が不明な場合は「不明」と扱い、成功と断定せず再送しないでください。
この方針は、別の本来の業務処理が失敗したことを隠す指示ではありません。

端末用JSON、イベント本文、機械用IDは、通常のチャットに表示しないでください。
必ず専用ツールで送り、ツールが不通でもチャットへ代替投稿しないでください。
```

## 選択肢で答えられる質問

同じDotへ以下も渡します。

```text
通常の会話で本当に選択が必要な場合は、その質問を
device_publish_question で端末にも送ってください。
端末を動かすためだけの余分な質問は作らないでください。

本文は短い日本語、選択肢は1〜4個、表示名はなるべく6〜8文字以内にします。
選択肢は「はい／いいえ」「今すぐ／あとで」など、答えそのものにしてください。
対象や重要な条件を短縮で失わないでください。画面に収まらない重要な確認は、
通常のチャットで詳細を説明し、端末の短い表示だけで承認を取らないでください。

質問ごとに一意な question_id、候補ごとに一意な id を使います。
同じ質問IDで本文や候補を変えないでください。
回答が未受領の質問を、別の質問で勝手に置き換えないでください。
端末では選択肢を1回押せば回答が確定します。
追加の「送信する」や確認画面を要求しないでください。

端末の回答は通常の質問への回答として扱います。
OSやプラグインの権限、外部への送信、課金などに必要な正式な承認を、
端末の選択だけで代替したり、別の操作への許可に拡大したりしないでください。
```

## 回答イベントの受信時に渡す指示

`device.answer` の購読／イベント処理に以下の指示を設定します。通常会話の指示を保存するだけでは、イベント処理の指示まで更新されるとは限りません。

```text
受信した device.answer は新着通知として扱い、回答の正本は
device_read_answer(question_id) で確認してください。
自分が device_publish_question で送った質問の範囲だけ読みます。

読んだ interaction_id が送信済み question_id と一致し、
choice_id がその質問の候補に含まれ、source が real であることを確認します。
request_id と既存の receipt_id も確認します。
イベント本文が使える場合は、本文の質問・選択肢・リクエストIDも照合します。
イベント本文がない場合、通知だけで選択を推測せず、
送信済み質問に一致する実回答を専用ツールで確認できた時だけ処理します。

実回答を確認したら、他の調査や保存、端末への受領通知より先に、
通常チャットへ「デバイスから『回答の表示名』を受け取ったよ」のように
短く知らせてください。同じ回答を既にチャットへ通知していれば重複通知しません。
その後、質問の対象範囲と既存の許可に沿って回答を処理します。

device_record_receipt には実際に読んだ interaction_id、choice_id と、
request_id に基づく安定した receipt_id、短い受領文を指定します。
受領済みの過去回答を再処理せず、未受信の回答や受領を作らないでください。
送信結果が不明なら自動再送しないでください。

この1件を処理し終えても、回答イベントの購読を停止・削除しないでください。
無関係な過去質問は読みません。端末の通信失敗は静かにスキップします。
端末用のJSONや機械データを通常チャットや他のサービスへ投稿しません。
```

## この指示で保証できることの限界

実際の運用では、Dotが回答の受領表示を残そうとして、その後の通常返信の要約送信を省くことがありました。接続が正常でもツールを呼ばなければ端末は更新されません。そのため、返信後の判定と受領済み／未回答の区別を明示しています。

指示の保存は、全返信を捕捉して強制実行するhookの実装とは異なります。調査したDotの公開されたツールには、そのhookを登録する機能は見つかりませんでした。絶対に漏れない仕組みが必要なら、実際のチャット送信処理に端末処理を組み込むか、チャット送信ログと端末処理の記録を独立して照合する必要があります。このリポジトリはそのチャット送信側の実装を含みません。

端末へのツール送信が成功したこと、画面が更新されたこと、Dotが回答を処理したことは別々に確認します。[通常会話からの往復確認](normal-chat-device-flow.md)を使って、自分のDotと端末で検証してください。
